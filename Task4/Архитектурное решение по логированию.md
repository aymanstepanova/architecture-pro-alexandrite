# Архитектурное решение по логированию

## 1. Контекст и цель

Сейчас инциденты и «зависшие» заказы разбираются по словам клиентов и операторов. Это увеличивает нагрузку поддержки и время восстановления, а также приводит к потере контрактов и росту негатива.

Цель: внедрить **централизованное структурированное логирование** и базовый контур анализа (поиск, дашборды, алерты), чтобы:

* быстро восстанавливать картину событий по заказу;
* уменьшить MTTR и количество “ручных расследований”;
* выявлять перегрузки/аномалии (скачки заказов, DDoS-подобные пики, “застревание” в статусах).

---

## 2. Какие системы покрываем сбором логов

По текущей C4-диаграмме сбор логов требуется из:

**Приложения**

* **Shop API** (Spring Boot) - ключевой вход B2C заказов, загрузка 3D.
* **CRM API** (Spring Boot) - подтверждение производства, закрытие заказа.
* **MES API** (C#) - расчёт цены, назначение/взятие заказа оператором, статусы производства/доставки.
* (Опционально) фронтенды Internet Shop / CRM / MES - в виде *client-side error logs* и *audit действий UI* (не заменяют серверные).

**Интеграции и инфраструктура**

* **RabbitMQ** (Messages Queue) - публикация/потребление событий по заказам между системами.
* **3D files storage (S3-like)** - события загрузки/скачивания, ошибки доступа, размер/тип.
* **PostgreSQL (Shop DB, MES DB)** - медленные запросы/ошибки/пулы подключений (на уровне DB и/или драйвера).
* ОС/контейнерные логи инстансов (пока EC2-like) - минимум для расследований (OOM, рестарты, диски).

## 3. Список необходимых логов уровня INFO

### 3.1. Сквозные принципы (единый формат)

Все прикладные логи пишем **структурировано (JSON)** и добавляем обязательные поля:

* `timestamp`
* `service` (shop-api / crm-api / mes-api / rabbitmq)
* `env` (dev/release/prod)
* `level`
* `trace_id`, `span_id` *(если трейсинг есть - связываем лог и трассу)*
* `request_id` *(если нет трассировки - как минимум correlation id)*
* `order_id` *(если применимо)*
* `customer_id` *(только если разрешено политикой; лучше псевдоним/хэш)*
* `actor` (customer/seller/operator/api_user/system)
* `event` (короткое имя события)
* `duration_ms` *(для операций с измеримой длительностью)*

### 3.2. Shop API (INFO)

* `order_initiated` - создана корзина/заказ (INITIATED): `order_id`, `customer_id(hash)`, `source` (web), `ip_country`(опц), `user_agent`(опц).
* `file_upload_started` - старт загрузки 3D: `order_id`, `file_size`, `file_type`.
* `file_upload_completed` - успешная загрузка: +`s3_object_key`, `duration_ms`.
* `file_upload_failed` - неуспешная загрузка (уровень **WARN/ERROR** см. ниже), но факт события можно фиксировать и на INFO в виде “итога” с `result=fail`.
* `order_submitted` - SUBMITTED: `order_id`, `items_count`, `has_3d_file=true/false`.
* `outbox_event_published` (если внедрим outbox) - событие заказа отправлено в очередь: `order_id`, `event_type`, `message_id`.

### 3.3. MES API (INFO)

* `price_calculation_requested` - начат расчёт: `order_id`, `model_polygons`(если есть), `priority`(если появится).
* `price_calculation_completed` - PRICE_CALCULATED: `order_id`, `duration_ms`, `price`, `currency`.
* `price_calculation_timeout` - итог с `result=timeout` (уровень WARN/ERROR).
* `order_assigned_to_operator` - назначение/взятие в работу: `order_id`, `operator_id(hash)`.
* `manufacturing_started` - MANUFACTURING_STARTED: `order_id`, `operator_id(hash)`.
* `manufacturing_completed` - MANUFACTURING_COMPLETED: `order_id`, `duration_ms`.
* `packaging_started` - PACKAGING: `order_id`.
* `shipped` - SHIPPED: `order_id`, `delivery_provider`, `tracking_id(masked)`.

### 3.4. CRM API (INFO)

* `manufacturing_approved` - MANUFACTURING_APPROVED: `order_id`, `seller_id(hash)`.
* `order_closed` - CLOSED: `order_id`, `closed_reason` (delivery_confirmed/manual), `seller_id(hash)`.

### 3.5. RabbitMQ / интеграция (INFO)

* `message_published` - публикация: `exchange`, `routing_key`, `message_id`, `order_id`, `payload_schema_version`.
* `message_consumed` - потребление: те же поля + `consumer`, `duration_ms`.
* `message_requeued` / `message_dead_lettered` - факт ретрая/ухода в DLQ (WARN/ERROR по обстоятельствам).
* `duplicate_message_detected` - если будет идемпотентность и детект дублей.

### 3.6. Доступ/безопасность (INFO, но аккуратно)

* `authn_success/authn_failed` - только агрегируемо и без чувствительных деталей.
* `permission_denied` - отказ в доступе к заказу/операции: `actor`, `resource`, `order_id`(если ок), `reason_code`.

## 4. Другие уровни логирования и когда

* **DEBUG**: только dev/release, для временной диагностики; в prod выключен по умолчанию и включается точечно/на короткое окно.
* **WARN**: деградации и “почти инциденты”
  Примеры: таймаут расчёта цены, превышение SLA по операции, повторное сообщение, частичные ошибки интеграций.
* **ERROR**: ошибки, влияющие на корректность процесса или данные
  Примеры: не удалось сохранить статус, не удалось опубликовать событие, падение обработчика очереди.
* **FATAL/CRITICAL** (если принято): сервис не может продолжать работу (миграции, конфиг, недоступен DB и нет graceful-degradation).

## 5. Мотивация

### 5.1. Зачем это компании

* Быстрое расследование “где застрял заказ” по `order_id` без угадываний и пересказов.
* Снижение нагрузки на поддержку и разработку (меньше ручных запросов “посмотрите логи на инстансе”).
* Контроль качества интеграций MES <-> CRM через RabbitMQ (самое “скользкое” место).
* Раннее выявление перегрузок: всплески заказов от API-партнёров, деградации расчёта стоимости и дашборда MES.

### 5.2. Метрики, на которые влияет внедрение

Технические:

1. **MTTR** (Mean Time To Recover) по инцидентам заказов.
2. **Доля запросов с ошибкой** (5xx/timeout) по сервисам.
3. **Latency** критичных операций (upload 3D, price calculation, publish/consume).

Бизнес:
4) **Доля заказов, “застрявших” в статусе** дольше целевого SLA (например, SUBMITTED->PRICE_CALCULATED).
5) **Количество обращений в поддержку на 1000 заказов** (и время первого ответа).

## 6. Приоритизация: что внедряем сначала (логи и трейсинг)

Команда не успеет покрыть всё сразу, поэтому делаем по этапам.

### Этап 1 (самое критичное для “зависаний”)

1. **MES API** - расчёт цены (2–30 минут), статусы производства/отгрузки, нагрузка дашборда.
2. **RabbitMQ** - события между MES и CRM, риск потерь/дублей.
3. **CRM API** - подтверждение/закрытие заказа.

Почему: именно здесь заказ чаще всего превращается в “непонятное состояние”, а партнёрские заказы усилили проблему.

### Этап 2

4. **Shop API + S3-хранилище** - загрузка 3D, SUBMITTED, публикация событий.
5. **PostgreSQL (все)** - медленные запросы, ошибки, пулы подключений.

### Этап 3

6. Логи фронтендов (ошибки JS, перфоманс), системные логи хостов/контейнеров, расширенная аналитика.

## 7. Предлагаемое решение

### 7.1. Технологии и компоненты

Цель - централизованный сбор, поиск, дашборды, алертинг.

**Вариант по умолчанию (open-source и cloud-friendly):**

* Log shipper на хостах/в k8s: **Fluent Bit** (или Fluentd)
* Хранилище и поиск: **OpenSearch**
* Визуализация: **OpenSearch Dashboards**
* Алерты: **OpenSearch Alerting** + уведомления в почту/мессенджер (например, Telegram)

**Схема потоков**

* shop-api / crm-api / mes-api / rabbitmq / db -> Fluent Bit -> OpenSearch (индексы по сервисам/окружениям) -> Dashboards/Alerting

### 7.2. Изменения в сервисах

* Включить **structured logging (JSON)**:

    * Spring Boot: Logback encoder (JSON), MDC для `request_id/trace_id/order_id`.
    * C#: Serilog (JSON), enrichment для `request_id/trace_id/order_id`.
* Ввести единый **correlation id**:

    * принимать `X-Request-Id`/`traceparent` от клиента/шлюза,
    * прокидывать между сервисами и в сообщения RabbitMQ (headers).
* Для RabbitMQ:

    * логировать publish/consume,
    * добавить `message_id`, `schema_version`,
    * подготовить DLQ и логировать уход в DLQ.

### 7.3. Обновление схемы (что добавить на C4)

Добавляем:

* `Log Shipper (Fluent Bit)`
* `OpenSearch Cluster`
* `Dashboards + Alerting`

Новые связи:

* Каждый backend + RabbitMQ + (опционально) DB -> Log Shipper -> OpenSearch -> Dashboards/Alerting -> уведомления администраторам.

## 8. Политика безопасности логов

1. **Запрещено писать в логи**:

    * персональные данные в открытом виде (ФИО, телефон, email),
    * содержимое 3D-файлов,
    * токены/пароли/сессионные данные,
    * платежные данные (если появятся).

2. **Маскирование/псевдонимизация**:

    * `customer_id`, `operator_id`, `seller_id` - хэш/псевдоним,
    * `tracking_id` - маска (последние 4 символа),
    * поля, похожие на секреты, режем фильтрами shipper’а (regex).

3. **Доступ**:

    * RBAC по ролям: support (read-only, ограниченный набор индексов), dev (read-only свои сервисы), admin (управление алертами/шаблонами).
    * аудит доступа к логам (кто искал/экспортировал).

4. **Сегрегация окружений**:

    * отдельные индексы/кластеры для prod и non-prod (минимум - разные индексы и политики доступа).

## 9. Политика хранения логов

### 9.1. Индексация

* Индексы по шаблону:
  `prod-shop-api-YYYY.MM.DD`, `prod-mes-api-YYYY.MM.DD`, `prod-crm-api-YYYY.MM.DD`, `prod-rabbitmq-YYYY.MM.DD`
  Аналогично для release/dev.

### 9.2. Retention (пример, настраивается по факту объёма)

* **Hot**: 14-30 дней (быстрый поиск, активные расследования)
* **Warm**: до 90–180 дней (менее быстрый поиск)
* **Cold/Archive**: выгрузка в объектное хранилище (S3-like) для редких разборов и комплаенса (если нужно)

### 9.3. Оценка размера (подход)

* сначала включить Stage-1 сервисы и измерить реальный EPS/GB-day,
* затем утвердить retention и лимиты по индексам (Index Lifecycle Policy).

## 10. Превращаем “сбор логов” в “анализ логов”

### 10.1. Алертинг (минимум)

* Spike по `order_submitted` / `price_calculation_requested` (аномальный рост).
* Рост `ERROR`/`WARN` по сервисам.
* Увеличение `duration_ms` для `price_calculation_completed` (p95/p99).
* Рост `message_dead_lettered` / `message_requeued`.
* “Застревание статусов”: нет события следующего статуса в течение SLA (реализуем сначала простыми правилами по логам, позже - через метрики/трейсы).

### 10.2. Поиск аномалий

* базово: пороговые правила (rate/threshold),
* затем: ML/детекторы аномалий OpenSearch (если оправдано объёмом и ценностью).

## 11. Дополнительное задание: критерии выбора технологии

| Критерий                  | ELK (Elastic)                         | OpenSearch                                  | Splunk                  |
|---------------------------|---------------------------------------|---------------------------------------------|-------------------------|
| Лицензия                  | Elastic License (ограничения)         | Apache 2.0                                  | Проприетарная           |
| Стоимость владения        | Средняя/высокая (особенно enterprise) | Ниже (open-source)                          | Высокая                 |
| Поиск/дашборды            | Очень зрелые                          | Зрелые                                      | Очень зрелые            |
| Алертинг/анализ           | Зрелый (часть функций платно)         | Есть, развивающийся                         | Очень сильный           |
| Экосистема/интеграции     | Огромная                              | Большая (совместимость с частью экосистемы) | Большая, но “вендорная” |
| Удобство эксплуатации     | Среднее                               | Среднее                                     | Высокое (но платное)    |
| Vendor lock-in            | Средний                               | Низкий                                      | Высокий                 |
| Подходит под рост/масштаб | Да                                    | Да                                          | Да                      |

**Выбор для “Александрита” сейчас:** **OpenSearch + Fluent Bit + Dashboards/Alerting**, как баланс стоимости, лицензии и достаточной зрелости. ELK возможен, но нужно учитывать лицензионные и бюджетные ограничения. Splunk - оправдан при готовности платить за “всё из коробки”.
