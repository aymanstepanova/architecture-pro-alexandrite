# Выбор и настройка мониторинга в системе

## 1. Контекст и текущее состояние

Сайт "Александрит" подключён к Яндекс Метрике, которая покрывает пользовательский путь B2C на сайте.
С момента запуска оформления заказов через API (B2B) значимая часть бизнес-процессов перестала быть видна:

* заказы могут приходить вне сайта;
* проблемы возникают после отправки запроса - в CRM, MES и очередях;
* расчёт стоимости может занимать от нескольких минут до десятков минут;
* часть заказов теряется или надолго "застревает" в статусах.

Текущая архитектура включает:

* online-shop API,
* CRM API,
* MES API,
* асинхронное взаимодействие через RabbitMQ,
* единичные инстансы приложений и БД.

UI-метрики больше не отражают реальное состояние бизнеса.

---

## 2. Мотивация

### 2.1. Зачем системе нужен мониторинг

Мониторинг необходим для решения конкретных бизнес-проблем:

1. **Снижение потерь заказов**
   Сейчас потеря или зависание заказов выявляется по жалобам. Мониторинг позволяет обнаруживать такие ситуации автоматически.

2. **Контроль сроков и узких мест**
   Долгие расчёты стоимости и очереди напрямую влияют на скорость выполнения заказов.

3. **Поддержка B2B-направления**
   API-клиенты ожидают предсказуемость и SLA. Без мониторинга невозможно управлять качеством сервиса.

4. **Снижение операционной нагрузки**
   Проблемы ищутся вручную и постфактум. Мониторинг переводит систему в проактивный режим.

### 2.2. Польза для бизнеса

* меньше потерянных заказов;
* быстрее выявление и устранение проблем;
* прозрачные цифры для принятия решений;
* повышение доверия B2B-клиентов.

---

## 3. Выбор подхода к мониторингу

В системе используются разные типы нагрузки, поэтому применяется комбинированный подход:

| Компонент                 | Подход                 |
|---------------------------|------------------------|
| API (shop, CRM, MES)      | RED                    |
| RabbitMQ                  | USE                    |
| Ресурсы (CPU, память, БД) | USE                    |
| Сквозные бизнес-процессы  | Четыре золотых сигнала |

---

## 4. Выбранные метрики для отслеживания

### 4.1. RabbitMQ

#### Number of dead-letter-exchange letters in RabbitMQ

**Зачем**
Индикатор потери сообщений и ошибок обработки.

**Бизнес-смысл**
Сообщение в DLQ = потенциально потерянный заказ.

**Ярлыки**

* queue_name
* message_type
* error_reason

---

#### Number of message in flight in RabbitMQ

**Зачем**
Показывает backlog и перегрузку консьюмеров.

**Бизнес-смысл**
Рост in-flight сообщений означает задержку обработки заказов.

**Ярлыки**

* queue_name
* consumer_group

---

### 4.2. API (online-shop, CRM, MES)

#### Number of requests (RPS) for shop / CRM / MES API

**Зачем**
Контроль нагрузки и корреляция с деградацией.

**Ярлыки**

* endpoint
* http_method

---

#### Number of requests (RPS) per user

**Зачем**
Контроль B2B-клиентов и защита от перегрузки.

**Бизнес-смысл**
Один клиент не должен нарушать работу всей системы.

**Ярлыки**

* client_id
* client_type (b2c / b2b)

---

#### Response time (latency) for shop / CRM / MES API

**Зачем**
Latency растёт раньше, чем появляются ошибки.

**Ярлыки**

* endpoint
* http_status

---

#### Number of HTTP 200 / Number of HTTP 500

**Зачем**
Базовый контроль стабильности API.

**Бизнес-смысл**
Рост 500 напрямую влияет на потери заказов.

**Ярлыки**

* endpoint
* error_type

---

### 4.3. Ресурсы приложений

#### CPU % for shop / CRM / MES API

#### Memory Utilisation for shop / CRM / MES API

**Зачем**
Контроль перегрузки и утечек ресурсов.

**Бизнес-смысл**
Перегруженное приложение перестаёт обслуживать заказы.

---

#### Number of simultaneous sessions

**Зачем**
Понимание параллельной нагрузки.

**Бизнес-смысл**
Рост сессий без роста RPS - признак зависших операций.

---

### 4.4. Базы данных

#### Memory Utilisation for shop db / MES db

#### Number of connections for shop db / MES db

**Зачем**
Контроль насыщенности БД.

**Бизнес-смысл**
Недоступная БД = остановка бизнеса.

---

#### Size of shop db instance

#### Size of MES db instance

**Зачем**
Прогноз роста и планирование ресурсов.

---

### 4.5. Сетевые метрики

#### Kb transferred / Kb provided (sent / received)

**Зачем**
Выявление аномалий трафика и проблем интеграций.

---

## 5. План действий (драфт технического задания)

1. Развернуть time-series базу метрик (например, Prometheus).
2. Развернуть систему визуализации (Grafana).
3. Настроить сбор метрик:

    * API,
    * RabbitMQ,
    * БД,
    * инфраструктура.
4. Инструментировать приложения для экспорта метрик.
5. Добавить correlation_id в:

    * HTTP-заголовки,
    * сообщения RabbitMQ,
    * логи и метрики.
6. Настроить мониторинг очередей и DLQ.
7. Настроить алерты на ключевые метрики.
8. Подготовить runbook’и реагирования.

## 6. Дополнительное задание: показатели насыщенности

### 6.1. Пороговые значения

| Компонент | Метрика               | Порог           |
|-----------|-----------------------|-----------------|
| API       | CPU %                 | >80%            |
| API       | Memory Utilisation    | >75%            |
| DB        | Number of connections | >80% лимита     |
| RabbitMQ  | Messages in flight    | стабильный рост |
| RabbitMQ  | DLQ                   | >0              |

---

### 6.2. Реакция системы

**Warning**

* уведомление команды;
* автоматический тикет.

**Critical**

* создание инцидента;
* автоматическое масштабирование (если возможно);
* уведомление ответственного инженера;
* при росте DLQ - включение деградационного режима.

**Бизнес-логика**
Лучше временно ограничить приём заказов, чем потерять их безвозвратно.

---

## 7. Итог

Данный набор мониторинга:

* покрывает ключевые риски потери заказов;
* связывает технические метрики с бизнес-результатом;
* создаёт основу для SLA и роста B2B-направления;
* минимально достаточен и масштабируем.
