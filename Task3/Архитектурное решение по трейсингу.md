# Архитектурное решение по трейсингу (Александрит)

## Контекст и цель
В «Александрите» заказ проходит через несколько систем (Online shop → MES → CRM, плюс интеграции через RabbitMQ и API). Из‑за асинхронности и долгих операций (расчёт цены 2–30 минут) команда теряет прозрачность: где «живёт» заказ сейчас, на каком шаге он завис, было ли сообщение в очереди, дошёл ли статус до следующей системы.

Цель решения — сделать **сквозную наблюдаемость “journey” заказа** (end‑to‑end), чтобы за 1–2 клика ответить на вопросы:
- где сейчас заказ и последний подтверждённый статус;
- какой сервис «держит» заказ и почему (ошибка/таймаут/ретраи/потеря сообщения);
- как долго занимает каждый этап (в т.ч. расчёт цены, взятие в работу, упаковка и т.д.).

Источник архитектурного контекста: описание кейса «Александрит» (спринт 6) — три приложения (Online shop, CRM, MES), обмен через RabbitMQ, S3‑хранилище 3D‑файлов, БД Shop/CRM/MES. fileciteturn0file0L1-L33

## 1. Что покрываем трейсингом (где заказ “ломается/зависает”)

### 1.1. Критические точки по жизненному циклу заказа
**Online shop**
- INITIATED → FILE_UPLOADED → SUBMITTED  
Риски:
- не сохранили/потеряли 3D‑файл, неконсистентность между записью заказа и загрузкой файла;
- SUBMITTED “есть” в Shop DB, но дальше процесс не двинулся (нет сообщения/нет вызова в MES).

**MES**
- PRICE_CALCULATED (долгая операция 2–30 минут)  
Риски:
- зависание/ошибка расчёта, нет понятного идентификатора “какой именно расчёт” связан с заказом;
- падение/перезапуск сервиса → пропажа контекста обработки;
- высокая нагрузка → очереди на обработку растут, SLA срывается.

- MANUFACTURING_STARTED / COMPLETED / PACKAGING / SHIPPED  
Риски:
- оператор “видит” заказ поздно (плохая производительность dashboard), не берет в работу;
- статус меняется в MES, но не доезжает в CRM (потеря сообщения / некорректная обработка).

**CRM**
- MANUFACTURING_APPROVED  
Риски:
- заказ подтверждён в CRM, но не запускается производство (интеграция/очередь/ошибка консюмера).

- CLOSED (в т.ч. внешняя доставка/ручное закрытие)  
Риски:
- закрытие не происходит или происходит “двойным” событием, статусы расходятся между системами.

**Интеграции и транспорт**
- RabbitMQ (топики/очереди по заказам и статусам)  
Риски:
- потеря сообщения, “завис” consumer, повторная доставка, DLQ, reorder событий.
- отсутствие общего correlation-id/trace-id между продюсером и консюмером.

- API для внешних пользователей (API user → MES/Shop)  
Риски:
- запросы и события по заказам внешнего партнёра не коррелируются с внутренним потоком.

- S3‑storage 3D‑файлов  
Риски:
- файл есть, но не тот (перезапись/версионирование), не сходится размер/хэш;
- MES не может скачать/прочитать файл для расчёта.

### 1.2. Компоненты, которые обязательно инструментируем
1) Shop API (Spring Boot)  
2) CRM API (Spring Boot)  
3) MES API (C#)  
4) RabbitMQ продюсеры/консюмеры в Shop/CRM/MES  
5) Работа с S3 (upload/download, метаданные/хэши)  
6) Входные точки: UI (опционально — browser tracing для фронтов), внешнее API

## 2. Какие данные должны попадать в трейсинг

### 2.1. Обязательные поля (span attributes / baggage)
**Корреляция**
- `trace_id`, `span_id`, `parent_span_id`
- `order_id` (единый идентификатор заказа во всех системах)
- `correlation_id` (для RabbitMQ и интеграций; дублируем в message headers)
- `request_id` (на входе API/GUI, если уже есть)
- `customer_id` / `seller_id` / `operator_id` / `api_client_id` (если применимо)
- `environment` (dev/release/prod), `service.name`, `service.version`, `host`, `instance_id`

**Бизнес‑контекст заказа**
- `order_status_from`, `order_status_to`
- `channel` = `B2C` | `B2B_API`
- `product_type` (готовое/на заказ), `has_3d_model` (bool)

**Интеграции**
- HTTP: `http.method`, `http.route`, `http.status_code`, `net.peer.name`
- RabbitMQ: `messaging.system=rabbitmq`, `messaging.destination` (exchange/queue),
  `messaging.operation` (publish/consume), `message_id`, `redelivered`, `retry_count`,
  `dlq` (true/false)
- S3: `storage.bucket`, `storage.object_key`, `storage.operation` (put/get),
  `file_size_bytes`, `file_hash` (например SHA-256), `etag`, `version_id` (если есть)

**Длительные операции**
- `mes.price_calc.polygons_count` (если доступно), `price_calc.duration_ms`,
  `price_calc.result` (success/fail/timeout), `price_calc.error_type`

### 2.2. Логи и ошибки
- stacktrace — **в логах**, а в трейсах только ссылка/ошибка класса (чтобы не светить лишнее)
- для ошибок: `error=true`, `exception.type`, `exception.message` (без PII)

### 2.3. Что НЕ кладём
- персональные данные клиента (ФИО, телефоны, email, адрес) — только безопасные идентификаторы
- содержимое 3D‑файлов; максимум — хэш/размер/ключ

## 3. Мотивация

### 3.1. Почему трейсинг нужен
- **Сокращение времени расследования**: вместо “пинг‑понга” между командами — один trace заказа.
- **Снижение потерь заказов**: видим разрывы потока (сообщение не доставлено, consumer умер).
- **Контроль SLA по этапам**: отдельно измеряем “где именно” теряем недели (подтверждение, расчёт цены, взятие в работу, доставка).
- **Улучшение UX операторов и продавцов**: причины медленной первой страницы MES становятся измеримыми (узкое место — БД/сервис/очередь).

### 3.2. Метрики, на которые повлияет внедрение
Технические (пример 3–5):
1) **p95/p99 latency** по ключевым операциям: `POST /orders`, `price_calculation`, `publish/consume status events`
2) **Доля ошибок** по операциям (5xx, timeouts, retries) в разрезе сервисов
3) **Очереди RabbitMQ**: рост backlog / `messages_in_flight`, `dlq_count` (как симптом потерь/редоставок)
4) **End-to-end duration** заказа: от `SUBMITTED` до `SHIPPED/CLOSED`
5) **Доля “stuck orders”**: заказы без смены статуса > N часов/дней

Бизнес:
1) **Снижение просрочки заказов** (SLA “≤ 3 недели”)
2) **Снижение компенсаций/возвратов** из‑за “пропавших” заказов
3) **Удержание B2B контрактов**: прозрачность и прогнозируемость статусов по API‑заказам

## 4. Предлагаемое решение

### 4.1. Технологии и подход
- Стандарт: **OpenTelemetry (OTel)** для распределённого трейсинга.
- Протокол: **OTLP** (gRPC/HTTP) от сервисов до коллектора.
- Backend для трасс: **Jaeger** *или* **Grafana Tempo** (выбор зависит от того, что проще поддерживать DevOps‑ом).
- Визуализация/поиск: Jaeger UI или Grafana (Tempo datasource).

### 4.2. Что дорабатываем в приложениях
**Shop API (Spring Boot)**
- подключить OTel Java agent *или* SDK (через Spring Boot autoconfig);
- автоматическая генерация `trace_id` на входе и прокидывание дальше;
- при публикации в RabbitMQ добавлять headers: `traceparent` (W3C), `correlation_id`, `order_id`.

**CRM API (Spring Boot)**
- аналогично Shop API;
- консюмер RabbitMQ: извлекать `traceparent`/`correlation_id`, продолжать trace;
- фиксировать переходы статусов (span/evt).

**MES API (C#)**
- подключить OTel .NET SDK;
- обернуть “расчёт цены” отдельным span с атрибутами длительной операции (polygons_count, duration, result);
- при публикации/консюмировании RabbitMQ — то же правило заголовков.

**Общее**
- единое правило: **order_id обязателен** в span attributes, иначе trace бесполезен.
- добавить “event” на смену статуса (span event) + запись в лог (для аудита).

### 4.3. Инфраструктурные компоненты
- **OpenTelemetry Collector** (центральная точка приёма: batching, sampling, retries, exporter).
- **Tracing Backend** (Jaeger/Tempo) с хранением трасс (retention, например 7–14 дней в проде).
- (Опционально) Sampling: tail-based для “медленных”/ошибочных traces, чтобы не утонуть в объёмах.

## 5. Дополнительное задание: автоматический мониторинг процесса прохождения заказа и алертинг

### 5.1. Идея
Из трасс мы строим “процессные” метрики: сколько заказов застряло в каждом статусе и сколько времени они там находятся.

Компонент **Order Flow Monitor**:
- периодически (или в near-real-time) анализирует traces/спаны по `order_id` и последним `order_status_to`;
- вычисляет:
  - “order stuck” (нет изменения статуса > N);
  - превышение SLA на этапах (например, `SUBMITTED -> PRICE_CALCULATED` > 40 минут);
  - рост ошибок/таймаутов по `price_calc`.
- публикует агрегированные метрики в **Prometheus**.

Далее:
- **Grafana** показывает дашборды:
  - распределение времени по этапам;
  - топ “самых долгих” заказов;
  - доля проблемных заказов по каналам B2C/B2B.
- **Alertmanager** отправляет алерты (почта/telegram/…):
  - “Stuck orders > X за 1 час”
  - “p95 price_calc > Y минут”
  - “DLQ messages > 0” или “redelivered rate > threshold”

## 6. Компромиссы и ограничения
- **Стоимость хранения**: трейсинг генерирует много данных (особенно при высокой RPS и длинных цепочках). Нужны sampling/retention.
- **Неполное покрытие**: если какой-то участок не инструментирован (например, внешняя транспортная компания), цепочка будет рваться.
- **Сложность внедрения в MES**: C# сервис может потребовать ручной инструментализации части участков (особенно вокруг долгих задач/очередей).
- **Сопротивление изменениям**: нужно договориться о едином `order_id` и правилах заголовков (иначе не сойдётся корреляция).
- **Чувствительность к качеству данных**: если статусы меняются “неатомарно” (сначала БД, потом событие), может быть несоответствие — нужна дисциплина outbox/идемпотентность (как следующий шаг).

## 7. Безопасность
- Доступ к UI (Grafana/Jaeger) только сотрудникам компании через корпоративную учётку (SSO/OIDC) и RBAC (например, роль “Поддержка”, “DevOps”, “Разработка”).
- Сегментация сети: OTel Collector и backend доступны только из внутренней сети/VPC.
- TLS/mTLS:
  - OTLP трафик сервисов → Collector по TLS (в идеале mTLS).
- Секреты (ключи, токены) — в секрет‑хранилище, не в конфиге.
- Санитизация данных:
  - запрет PII в trace attributes (политика + линтер/ревью);
  - фильтрация чувствительных полей на Collector (processors).
- Аудит доступа: логируем входы/изменения прав в системе наблюдаемости.
